# 性能与 CI 验证

本文件记录 v0.0.2 准备期间取得的测量与边界。构建通过、索引存在和实际性能改善是三个不同的结论。

## 缩略图队列查询

环境：Windows 主机的 Debian WSL2 ext4 构建目录，Intel Core Ultra 7 255H，Go 1.27.4，`GOMAXPROCS=8`，modernc.org/sqlite v1.62.0。

构造 20,001 条元数据记录：10,000 条缩略图已处理、10,000 条损坏且缩略图未处理、1 条健康待处理。没有创建或解码实际图片。每次查询读取第一批最多 200 个健康待处理 ID，并断言只返回预期记录。

```sh
go test ./internal/meta -run '^$' -bench BenchmarkPendingThumbsLargeLibrary -benchmem -count=3
```

| 指标 | schema 3 索引 | schema 4 索引 |
| --- | --- | --- |
| 三次 `ns/op` | 2,267,402 / 2,288,255 / 2,411,171 | 14,765 / 14,258 / 15,356 |
| 三次结果的中位数 | 2.288 ms/op | 0.014765 ms/op |
| 索引与游标 | 旧待处理索引按创建时间排列，与 ID 游标不匹配 | `images_thumb_pending (state=? AND id>?)` |
| 每次分配次数 | 19 | 19 |

该构造场景中，单次队列查询的中位数耗时约为原来的 1/155。它只说明这个查询的改善，不能换算为上传、解码、整个后台任务或用户界面的加速比；三次基准的中位数也不是线上请求延迟的 p50。

原索引只覆盖 `(created_at)`，包含损坏记录，与 ID 游标不匹配。单独换成 `(id)` 后，SQLite 仍选择状态/大小索引，测量没有改善。最终使用 `(state, id)`，仅覆盖活跃、未损坏且缩略图未处理的记录；保持原查询，让优化器自行选择。未使用 `INDEXED BY` 强制绑定索引。

迁移测试覆盖 schema 3 升级前备份、待处理记录保留、既有缩略图状态保留，以及修复损坏标记后的重新入队。首次升级会创建索引；这里没有测量百万级记录的索引创建耗时。

## 图片处理基线

使用现有 `internal/imaging/bench_test.go`，同一机器运行三次。该基准由固定种子生成 24 MP JPEG，与生产上传文件分布不同。

| 基准 | 三次结果的中位数 | 每次分配 |
| --- | --- | --- |
| 24 MP JPEG 缩略图 | 186.84 ms/op | 约 59.58 MB，37 次 |
| 24 MP JPEG 结构检查 | 376.62 μs/op | 约 65.6 kB，2 次 |
| PNG 结构检查 | 7.36 μs/op | 约 65.6 kB，2 次 |

本轮没有修改解码器，不宣称这些路径获得提速。缩略图 worker 并发仍为 1，像素限制也不等于固定内存上限。

## CI 关键路径

原流水线在变更检测后运行双架构测试，再启动交叉编译、E2E 和 Docker 构建。它们不消费测试任务的产物，因此等待关系并非构建所需。

新流水线让这些任务在变更检测后独立运行，`ci-ok` 仍要求全部成功；文档变更的显式跳过规则保持不变。actionlint 校验所有工作流。正式发布仍等待完整验证，不为了缩短耗时提前推送正式镜像。

基线运行 [44036971495](https://github.com/DejavuMoe/PicBerth/actions/runs/44036971495) 从 `changes` 启动到 `ci-ok` 完成为 3 分 31 秒。新流水线的耗时应以实际 Actions 运行记录为准；runner 排队、缓存和网络都可能变化，不承诺固定加速比例。

Docker 构建上下文排除 `.agents/`、`.github/` 和 `designs/`。正式镜像原本不会使用普通 BuildKit 缓存，现在也不再导出随后会丢弃的缓存；演练保留 OCI 归档以检查真实产物。
Go 模块与构建缓存以 `go.mod`、`go.sum` 为依赖键，不再因为独立的 pnpm 或 Node 锁定版本变化而全部失效；模块完整性验证与发布缓存隔离保持不变。

## 界面约束

本轮没有修改 `web/src/`、设计原型或设计规则。Vite 补丁升级后的 CSS 摘要与升级前一致；桌面与移动端操作继续使用既有 Playwright 测试验证。文档双语化不改变管理界面的简体中文语言。
